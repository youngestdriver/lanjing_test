# Bug 记录:题库爬取失败 —— 上游 `key1~key4` 字段类型不一致

- **日期**:2026-08-10
- **影响端**:iOS 练习题库爬取(更新题库/首次爬取);web 考试流程存在同一隐患(已一并修复)
- **现象**:更新题库时【资料分析（二）】机考题库反复爬取失败,该卷题目无法进入题库

---

## 1. 问题现象

用户反馈"更新题库"爬取失败。爬取日志(初版仅记录试卷级步骤)显示:

```
[00:33:18] 【资料分析（二）】机考题库 · 进入试卷 — 失败（服务器响应异常）
```

加重试与批次级诊断后,日志精确到:

```
[01:16:37] 【资料分析（二）】机考题库 · 进入试卷 — 失败（重试 2 次后仍失败；
第 37/60 批（5 题）响应无法解析，HTTP 200；
涉及题目：66b1f826ee9c165b6866b58d、…、6951e4d3ee9c160f50c4259b；
坏元素：6951e4d3ee9c160f50c4259b（字段类型不符）；
上游响应：[{"_id":"66b1f826ee9c165b6866b58d","key1":"0","key2":"1",…）
```

关键特征:

- **确定性复现**:01:16 与 02:44 两次独立运行,失败批次、失败元素完全一致(重试 3 次后仍失败,排除偶发);
- 失败批次位置随作答不同而变(00:50 为第 40 批、01:16 起为第 37 批)—— 上游每份作答的题目顺序不同,但每次必卡在**包含该特殊题的组合**;
- 坏元素诊断从"缺 question"类(00:50,旧版诊断)演变为"**字段类型不符**"(字段级诊断上线后)。

## 2. 排查过程

### 2.1 解析器排除

用收集器直连客户端(有效会话)抓取【资料分析（二）】的真实答题卡 HTML(503KB),分别用 JS 与 Swift 解析器验证组合归属:

- JS `parseExamHtml`:300/300 题全部正确分配 `combId`;
- Swift `ExamHTMLParser`(独立编译运行):同样 300/300,含失败元素 `6951e4d3…59b` 归属 comb `662b07f6ee9c16509b87c1d1`(15.5)正确。

→ 解析器无问题,请求应带 combId。

### 2.2 请求形状排除

带 combId 直接调用上游 `/exam/get_question_info/`(同一作答、同一组合):

- 无 combId:全部元素**缺 `parent_info`**,但 `question` 均在 —— 不是缺失字段导致;
- 带 combId:JS 端 5 个元素全部正常解码(question + parent_info 齐全)。

→ 请求形状正确,JS 端解码正常 —— 指向 Swift 端解码差异。

### 2.3 上游偶发误判

排查期间上游从本机多次连接超时,一度误判为"上游网络不稳",为此加了批次重试(见 §4.3)。重试后仍确定性失败,排除偶发。

### 2.4 字段级诊断 + 实测取证(定位根因)

字段级诊断上线后,失败元素报告"**字段类型不符**"(即 `_id`、`question` 均存在且为字符串,但仍有字段解码失败)。复现该组合请求,打印目标元素完整 JSON:

```json
{
  "_id": "6951e4d3ee9c160f50c4259b",
  "key1": "1",        // ← 正确答案:字符串
  "key2": 0,          // ← 错误答案:数字 !!
  "key3": 0,
  "key4": 0,
  "answer1": "<p>…</p>", "answer2": "<p>…</p>",
  "question": "<p>…</p>", "parent_info": "<p>…</p>",
  "test_ans_right": "A", …
}
```

## 3. 根因

上游 `/exam/get_question_info/` 返回的 `key1~key4`(正确性标志)**类型不固定**:

- 正确答案位:字符串 `"1"`;
- 错误答案位:数字 `0`(部分题目甚至全部为字符串,如 `"key1":"0","key2":"0","key3":"0","key4":"1"`)。

Swift 端 `QuestionDTO` 将四个字段声明为 `String?`,`JSONDecoder` 无法把数字 `0` 解码进 `String` → 该元素整体解码失败 → 整批失败 → 该卷爬取失败。

JS 端用 `q[k] === "1"` 严格比较:数字 `0 !== "1"` 恰好安全,因此收集器(JS)与 web 端从未暴露此问题;仅 Swift 端(练习爬取、iOS 考试答题)受影响。

## 4. 修复

### 4.1 解码宽容(核心修复)

| 端 | 文件 | 改动 |
|---|---|---|
| iOS | `Models/UpstreamDTOs.swift` | `key1~key4` 类型 `String?` → `StringValue?`(项目既有 string/number 兼容解码器,数字 `0` → `"0"`) |
| iOS | `Models/Question.swift` | 正确性判断 `key == "1"` → `key?.value == "1"` |
| iOS | `Networking/PracticeUpstreamClient.swift` | 练习映射 `$0.0 == "1"` → `$0.0?.value == "1"` |
| web | `apps/web/server.js` | 抓题循环 `q[k] === "1"` → `String(q[k]) === "1"`(防御数字 `1`) |
| bank | `apps/bank/lib/upstream.js` | 同上 |

### 4.2 字段级诊断(保留)

`APIClient.describeBatchFailure` 对坏元素逐字段说明原因(`缺 _id` / `缺 question` / `question 非字符串` / `字段类型不符`),下次同类问题日志可直接定位。

### 4.3 批次重试(保留,防御真实偶发)

iOS `fetchQuestionDTOs` 每批最多 3 次(间隔 3s,会话过期不重试),重试耗尽后日志前缀"重试 N 次后仍失败";web `server.js` 同步。JS 收集器原有 `withRetry`。

## 5. 验证

- **端到端**:抓取失败组合(comb `662b07f6ee9c16509b87c1d1`,含 `6951e4d3…59b`)的真实上游响应,用修复后的 Swift DTO 解码 → 5 个元素全部通过,`keys` 归一化为 `"0"/"1"`,正确答案全部识别;
- **单测**:
  - iOS 新增 `testDecodesMixedTypeKeysTolerantly`(字符串"1"+数字 0 混合、全数字两种形态)→ 145/145 通过;
  - web 61/61、bank 64/64 通过;
- 用户侧:重新"更新题库"后 14 份试卷全部爬取成功。

## 6. 经验与后续

- **上游数据形态不可信**:同一字段在不同题目上 string/number 混发,Swift 解码必须用 `StringValue` 类宽容解码器(项目已有,直接复用);
- **诊断日志的价值**:本次从"服务器响应异常"→ 批次+题号 → 字段级原因,每一步都依赖日志逐步收窄;后续再遇上游异常形态,优先扩充诊断而非猜测;
- 若上游再出现新的字段类型形态(`analysis`/`answerN` 等),按 §4.1 模式处理并补充测试。
